## 问题

### 1. 两级容器是同一个概念,却有两套动词

rubric 的概念篇已经写着「**段与 lane 是同一份词表的两级,规则相同**」:各自由一个 tag 标识,
带上那个 tag 就是归属,tag 在自己的作用域内唯一。但动词表完全不对称:

| | 段 | lane |
|---|---|---|
| 建 | `create` + `retag` 命名 | `declare`(建即命名) |
| 改名 | `retag` | **无** |
| 删 | **无**(只有 `close` 下架) | `undeclare` |
| 合并 | **无** | `merge` |

两级同一件事,四个格子里有三个不一致。每加一个机制,成本不只是它自己,还有它与既有全部机制的交互面 ——
这里的交互面已经开始按级数增长。

### 2. 用过的容器退不掉

- `undeclare` 在**任何成员 turn 还带着 tag 时拒绝**。生产库 101 条 lane,**零条**是空的,
  所以这个动词今天无处下口。
- 段**没有删除动词**。69 个段里 **54 个既无成员也无 lane** 是纯空壳,只能 `close` 下架,
  行留在库里、留在 console 里。
- 手工剥 tag 不是绕道:lane 自己的边仍然在两侧写着那个词,成员一停止携带,
  校验器 C2 就对每条边报子集违规;lane 一离开注册表,再报未声明违规。**C2 现在是 0。**

### 3. 词汇本身有问题

`段` 读起来像时间切片,实际是任务容器;`lane` 在一份中文 rubric 里是没翻译的行话。
两者都违反「用广泛认可、容易理解的词」。

### 4. 泳道命名太早,已经积出一批垃圾

E60 的 76 条泳道里,**21 条的成员集合是另一条的严格子集** —— v12 没有层级,
一条完全内嵌的泳道只能是父题在更细粒度上的重复。**20 条卡在 2 个成员**(定义下限),
绝大多数当天开当天结束。这不是「遗留杂乱」,是命名早于判断。

## 解法

**一个容器概念,两级,一套动词。**

1. **更名**:段 → **任务**,lane → **泳道**。只改读者可见的那层(rubric、工具描述、console、
   报表文本);表名、列名、代码标识符不动。
2. **五个动词两级通用**:`create` / `retag` / `merge` / `clear` / `delete`。
   `declare` 与 `undeclare` 退役,并入 `create` 与 `delete`。
3. **`force` 参数**:任何「能做但该先警告」的场合先报提示、拒绝执行,加 `force=true` 才成功。
4. **地址语法**:泳道用 `E<n>/#<tag>` 寻址,并入 recall 现有的选择器语法。

退役与新增之后的完整动词表:

| | 任务 `E<n>` | 泳道 `E<n>/#<tag>` |
|---|---|---|
| `create` | ✓ | ✓ |
| `retag` | ✓ | ✓ |
| `merge` | ✓ | ✓ |
| `clear` | ✓ | ✓ |
| `delete` | ✓ 仅空 | ✓ 仅空 |
| `attach` / `detach` | ✓ | — |
| `write` / `edit` | ✓ | — |
| `close` | ✓ | — |

**退役一个用过的容器有且只有两条路**,两条都不留孤儿:

- **`merge`** —— 把成员与信息交给另一个容器,自己变空,然后消失。改归属。
- **`clear`** —— 把 tag 从每个成员身上摘掉,并**删掉**归属于它的边;之后 `delete` 生效。去归属。
  任务级的 `clear` 在该任务**还有已声明泳道时拒绝**,并列出它们(见 D5)。

## 实现决策

### D1 —— 更名只动读者可见层

`段` → **任务**,`lane` → **泳道**。

改:rubric 两份正文、`remember` / `recall` / `timeline` / `note` 的工具描述、
console 的图例与面板文案、校验器报表文本、`CONTEXT.md` 词条。

**不改**:`segments` / `lanes` 表名与列名、TypeScript 标识符(`SegmentRecord`、`laneToken` …)、
`E<n>` 地址前缀、库里已存的任何数据。库里几千个 turn 的归属挂在现有词表上,
而重命名的收益全部在阅读侧 —— 让存储层跟着改名是纯粹的偶然复杂度。

`任务` 与本环境里的 subagent task 撞词,读者-facing 文本里靠上下文区分。

### D2 —— 泳道地址 `E<n>/#<tag>`

并入 recall 现有的地址语法,该语法今天认:`S<n>`、`S<n>/T<m>`、`E<n>`、`E<n>/T*`、
`E<n>/S<a>/T<b>`、`E<n>/S<a>/T<b>..S<c>/T<d>`、`T<n>`、`O<n>`。

`#` 开头与其中任何一种都不冲突。

**按名字,不按序号。** timeline 今天的 `E<n>/L<n>` 是 1-based 序号形式,
与 turn 上已经退役过两次的序号地址是同一个毛病 —— 同一个字符串在不同渲染下指向不同对象。
`E<n>/#<tag>` 成为**规范形式**;`E<n>/L<n>` 保留为交互挑选用的便利形式,但不作为可粘贴的地址。

一个地址同时是 recall 的读选择器和 `remember` 的写目标:选中它和操作它是同一句话。

**tag 的字符集必须收紧(peer #12)。** 今天 `checkCanonicalLaneTag` 只拒绝空、未 trim、
内部空白、非小写、非 NFC 和 `:` 前缀 —— **逗号是合法的**,而 recall 在解析前按逗号切分 `id`
以支持地址列表。于是 `E1/#a,b` 会被切成两个选择器,那条泳道**没有可用的规范地址**。

决定:canonical 谓词收紧到 `[a-z0-9-]`(NFC、小写、非空、不以 `-` 开头或结尾),
把选择器用到的每个分隔符 —— `,` `/` `#` `*` `.` —— 一并排除在外。
实测生产库 **104 个已声明 tag 全部落在这个字符集内**,非字母数字字符只出现过 `-`,
所以收紧**不破坏任何存量**。选择转向收紧而不是转义:转义会给一个人要手打的地址
引入编码层,而地址的全部价值就是可粘贴。

### D3 —— 动词映射与退役

- `declare` → `create`,目标由 `id` 的层级决定(`E<n>` 建任务,`E<n>/#<tag>` 建泳道)。
- `undeclare` → `delete`。
- `retag` 扩展到泳道。
- `merge` 扩展到任务。
- `clear` 新增,两级通用。

退役的两个词继续接受,但返回指向新词的拒绝,不静默转发 —— 与 `append`/`replace`
退役时的先例一致。

`create` 在两级上共用同一条前置:花名册里没有合适的就用 AskUserQuestion 问用户,
同意了才建,不静默新建。

**结算侧必须同批退役(peer #10)。** `note-settlement-membership-facade.ts` 有**自己的**
`action: z.enum(["declare","undeclare","merge"])` 和自己的写路径,只改主 `remember` 等于没改:
旧词在结算侧仍然成功执行,而结算提示与主 rubric 还在教它。三处 —— 结算枚举、结算提示、
rubric 正文 —— 与主工具同批改,否则退役只发生在一个入口上。

### D4 —— `delete` 只删空的

判据两条,都在写事务内重查:

- 任务:没有成员 turn(按 `getOwningSegmentId` 的归属口径)**且**没有已声明的泳道。
- 泳道:没有成员 turn 携带它的 tag —— 也就是 `undeclare` 今天的守卫,原样继承。

非空时拒绝,**报出数量,并指出两条出路**(`merge` 改归属 / `clear` 去归属)。
`delete` 本身**没有 `force`**:强删一个还活着的容器不是「需要警告的操作」,
是「用错了动词」,而两条正确的路都存在。

### D5 —— `clear`:去归属,并删边

**边的两侧必须按归属段解析,不能比较裸字符串(peer #4)。** 泳道身份是 `(容器, tag)`,
而边侧存的是**裸 tag 字符串**。E1 和 E2 都声明 `alpha` 时,一条 E1/alpha → E2/alpha 的边
两侧都写着 `alpha`,Rev 1 的「两侧都是这个 tag」会把它判成 E1 内部并删掉,毁掉 E2 的记录。

`mergeLaneTag` 已经做对了这件事:它用 `ownsSide()` 通过**端点自己的归属段**解析每一侧。
`clear` 复用同一个判断,不另写谓词。(生产库今天跨段同名泳道实测 **0 条**,所以这是潜伏缺陷
不是活缺陷 —— 但当前数据形态不是不变式。)

**泳道级 `clear(id="E<n>/#<tag>")`** 做两件事:

1. 从每个成员 turn 的 `tags` 里摘掉这个词(经由归属推导写回,不裸 `UPDATE`)。
2. **删掉两侧都解析到这条泳道的边行。**

第 2 条是本决策的要害。把边侧还原成未结算(`''`)看起来更保守,实际是把一批**无归属的边**
扔回 C1 那 1047 条的待结算队列,让结算再处理一遍一件已经作废的事 —— 用户判定为残留,
不是洁净清空。既然这条泳道整个作废,它内部的边一起走。

**两类边要 `force`,不是一类:**

- **跨泳道边**(一侧解析到它、另一侧解析到别的泳道):删掉会毁对方的记录。
- **半结算边**(一侧是它、另一侧是 `''`,peer #6):`''` 不是「别的泳道」,所以 Rev 1 的
  跨泳道警告**漏掉了它**。结算允许留下这种草稿且逐调用持久化,于是 `clear` 之后会剩一条
  指向已删泳道的边侧,报 E4/E6。它必须与跨泳道边同等对待。

生产库今天这两类都是 0 条,规则仍要写。

#### D5b —— 删完之后必须恢复 bare 行(Rev 3)

**Rev 2 把这条驳回了,理由是假的。** 我说这是「每一次边撤销都存在的既有不对称」——
不是。`db/citations.ts` 的 `restoreBareRowsForEmptiedPairs` 就是为它写的,撤销路径在调它,
它自己的文档开头写着:

> Ticket 10(peer 终审必改 3):**撤销不得让散文仍在断言的引用消失。**
> …「先分类一条引用、再撤销这个分类」会让这个 pair 一行都不剩,`↳` 透传和被引计数
> 悄悄丢掉一个正文仍在指名的目标。**修复放在撤销路径上**,而不是原语里。

那个不对称**已经修好了**。`clear` 是一条**新的公开批量撤销路径**,直接硬删会绕过这个修复,
把同一个缺陷原样引回来。

**决定**:批量删除之后、提交之前,把被清空的 pair **按引用方分组**,跑同一条
「重扫正文、正文仍指名则恢复 bare `text-ref` 行」的规则 —— 复用 `restoreBareRowsForEmptiedPairs`,
不另写。fixture 必须构造「被删的那行是这个 pair 的最后一条关系,而引用方正文原封未动」。

**任务级 `clear(id="E<n>")` 在该任务还有已声明泳道时拒绝**,并列出它们(peer #1)。

Rev 1 那句「任务级同理」是**无法实现的**:写闸的结构性规则是「泳道 tag 只能骑在已经带着
它所属任务 tag 的 turn 上」,所以从一个同时带 `[任务, alpha]` 的 turn 上只摘掉任务 tag,
会被闸拒;而边侧**根本不持有任务 tag**,「删掉该任务名下的边」没有对应的存储谓词。

所以任务级 `clear` 的前置是「泳道已清空」,不是递归销毁:先把每条泳道 `merge` 或 `clear` 掉,
任务变成无泳道,这时摘掉成员的任务 tag 才是安全的、且只动 `tags` 一处。
**拒绝优于隐式递归** —— 递归会让一次调用毁掉调用者没有指名的东西。

### D6 —— 合并任务:五个 population,而且顺序是硬的

`mergeLaneTag` 已经建立了泳道合并的形状(成员 tags、边两侧、注册表行,一个事务),
任务合并沿用它的纪律,**包括把守卫与操作配对** —— 光有「在一个事务里」的散文不够,
事务内的错误顺序产生同样的最终状态,事后无法分辨。

**归属有两个存储,选成员必须按归属而不是按 tag(peer #2)。** `create(members=[...])`
走 `reassignSegmentMembers`,**只写 `segment_members` 行,不给 turn 加任务 tag**;
`retag` 也故意不回溯历史成员。而 `getOwningSegmentId` 读的正是 `segment_members`。
Rev 1 说「携带 `from` 任务 tag 的成员」,会**一个这样的 turn 都搬不到**,
随后源任务删除时外键级联掉它的 `segment_members` 行,turn 变成无归属 —— 静默丢成员。

决定:成员集合按 `getOwningSegmentId(turn) === from` 取,**同时**补齐 tags,
让两个存储在合并后一致。

**顺序是硬约束(peer #3):泳道先于成员。** 把一个带 `[from, alpha]` 的成员改成 `[into, alpha]`
时,若 `alpha` 仍只声明在 `from` 名下,写闸会拒绝;绕过闸则造出非法状态。所以:

```
1a. 无重名的泳道:改挂 into                        ← 必须先于成员
1b. 重名的泳道:两行都留着,什么都不做              ← 见下
2.  成员:按归属取,改带 into 的 tag,归属推导写回
3.  字段:见 D7
4.  段级边:text-ref 派生重推,见 D9
5.  派生与授权状态 + 目标端 FTS 重建:见下
6a. 被清空的重名源泳道:配对守卫下删除
6b. from 离开注册表                                ← 守卫与它配对
```

**第 1 步必须分支,否则整个操作到不了第 2 步(Rev 3)。** Rev 2 写「重名走 D8 递归合并」——
**没有那个原语**:`mergeLaneTag(db, segmentId, from, into, …)` 只接一个 `segmentId`,
结算 facade 显式拒绝跨段泳道合并(「a lane's identity is (segment, tag), and merge folds
one lane into another inside ONE segment」),而 `UNIQUE(segment_id, tag)` 让「把源 `alpha`
改挂到已有 `alpha` 的目标」当场违约。

分支法**不需要新原语**,它借的正是 D5 刚修对的那件事:

- 重名时两行注册表都先留着;
- 成员照常搬到 `into` —— 目标的 `alpha` 已经声明在那里,写闸满足;
- 成员一搬,那条边**裸的侧 tag 就通过端点归属自动解析到目标**,不需要改一个字节;
- 源 `alpha` 此时已空,用与删除配对的守卫删掉(6a)。

**第 5 步必须包含目标端的 FTS 重建(Rev 3)。** Rev 2 只清了源的 FTS 行,没有在字段拼接
之后重建目标的投影。FTS 不会跟着 SQL 自动同步,而第 2 步的 `type` 重算可能在字段合并**之前**
就索引过一次目标。后果:合并后的卡片里能看见来自 `from` 的文本,`recall(query=…)` 却搜不到它,
要等下一次无关的写入。既有的段写者每次都在最后一次行更新之后调 `indexSegment` —— 照做,
并把目标的引用重推(citation reconciliation)一并放在最后。
测试断言:源的命中消失,目标的命中出现。

第 6 步的守卫(「此刻 `from` 还有成员吗」)必须**与删除写在一起**,与 `undeclareEmptiedLane`
同一形状:把它上移到成员重写之前,它就会抛,而不是留下一个谁也删不掉的任务。

**第五个 population:派生状态与写授权(peer #8/#9)。**

- **`memory_fts` 的 segment 行**没有外键也没有删除触发器,源任务删掉后它**永久留在全文语料里**,
  影响语料统计与排序。必须显式删。
- **`write_gate_reads` / `write_gate_stamps` / `write_gate_field_completeness`** 同样是多态表、
  没有段外键,源行会泄漏。
- **目标任务被改写的八个字段必须在同一事务内盖戳。** 否则一个在合并前完整读过
  `into.content` 的写者,其旧授权仍然有效,可以用合并前的文本覆盖回去,**静默抹掉刚导入的内容**。
  普通写路径本来就是原子地「查授权 + 盖戳」,合并必须走同一条。

**会话挂靠不迁移**(用户裁决):合并的本质是把成员和信息交给对方然后自己消失,
挂靠是会话侧的加载状态,不是容器的财产,跟着容器一起消失 —— peer 确认 `segment_attachments`
与 `segment_detachments` 都随源任务级联,与这条裁决一致。

### D7 —— 字段拼接口径

- 六个 row-list 字段(goal / constraints / decisions / done / next_steps / reference):
  `from` 的行追加在 `into` 的行之后,**完全相同的行去重**。
- `title`:保留 `into` 的。合并之后的容器只有一个名字。
- `content` / `insight`:散文,空行分隔追加。
- `status` / `revision`:`into` 的不动。
- **`type` 必须重算,不能冻结(peer #7)。** 它是从全部 `segment_members` **派生**的 facet,
  并参与 FTS 的 `extra` 索引;任何一次普通的成员迁移都会重算源与目标两侧。
  Rev 1 把它归进「派生或状态列:不动」是把派生值当成状态列了 —— 合并搬进来一批成员,
  目标的 `type` 就已经变了,冻结它只会让 facet 与成员长期不一致。

### D8 —— `force`:承认它只是覆盖开关

一个布尔参数,覆盖一整类「能做但该先看一眼」的拒绝。首批三处:

| 场合 | 不带 force | 带 force |
|---|---|---|
| 合并任务,两边有同名泳道 | 拒绝,**列出全部冲突名** | 同名的两条按 `(容器, tag)` 身份即同一条,递归走泳道合并 |
| `clear` 会删到跨泳道边**或半结算边** | 拒绝,列出受影响的边与对面泳道 | 照删 |
| 合并任务,双方都非空且体量相当 | (暂不设) | — |

**Rev 1 声称 `force` 的语义是「我已经看过这份清单」——那是布尔值载不动的(peer #11)。**
第一次调用就能带 `force=true`,清单从未渲染过,而且提出的那条突变测试区分不了这两种情况。

决定:**把语义写弱到它真实的样子** —— `force` 就是「即使有警告也继续」,
不假装是确认。不带 force 的调用**仍然必须**打印完整清单(那是它自己的产品,不是 force 的前提)。

**放弃的东西**:真正的「已确认」需要请求内的令牌或指纹(不带 force 的调用返回一个 token,
带上它才放行)。不做,因为这里的调用方是一个人在操作台前逐条跑,不是自动化管线;
令牌会把一次手工操作变成两次,收益不抵。这条**明确记为已知取舍**,不是遗漏。

### D9 —— `text-ref` 是派生的,不手工搬

892 条非 turn→turn 的边行里,**带泳道 tag 的是 0 条**。它们的 relation 全部为 `NULL`,
provenance 全部是 `text-ref` —— 散文里出现 `[S…]` / `[E…]` 时自动记下的引用索引,
不参与任何泳道计算。段上已有 `AFTER DELETE` 剪枝触发器。

**决定**:合并时随字段一起重新推导,不写搬运代码。字段文本搬到 `into` 之后,
`into` 的引用索引自然覆盖那些地址;`from` 的行随它一起被触发器剪掉。

### D10 —— 清掉 4 条异类边

`turn→segment` 与 `segment→segment` 里有 4 条 `provenance='judged'` 的行
(3 条 bare + 1 条 `verifies`,2026-08-13/14 写下)。v12 的关系图是 turn→turn,
这 4 条是词表收紧之前的残留。一次性删除,并在 schema 层收紧:
关系词(`relation IS NOT NULL`)只允许 turn→turn。

### D11 —— rubric 与 CONTEXT.md 同批更新

rubric 概念篇的「段 / lane」两条词条改名,并把「作用域内唯一」表述成**一条**规则的两级实例,
不是两条规则。行动原则篇里「不要静默新建」那条同时覆盖两级。

`CONTEXT.md` 的 `Lane` 词条今天仍描述 v10/v11 的 exact-set 身份(「其身份是它的精确 tag 集合」),
已被 v12 的单 tag 身份取代 —— 本批一并订正,而不是叠一层新词条上去。

## 测试决策

**好的测试只钉外部行为。** 这批的外部行为面很窄,几乎全部集中在一个已有接缝上。

### 接缝

**主接缝 —— `rememberTool`。** 五个动词全部经它进出,输入是参数对象,输出是文本结果。
现有 `tests/mcp/remember.test.ts` 已经用这个接缝覆盖了 `declare`/`undeclare`/`merge`,
新动词照同样的形状加即可 —— 不新开接缝。

**第二接缝 —— 地址解析。** `E<n>/#<tag>` 要被 recall 的选择器语法接受,
现有 recall 测试里已有逐形式的地址解析用例,新形式加在同一张表里。

**第三接缝 —— 结算侧的独立写路径(peer #13)。** Rev 1 说「两个接缝够了」是错的:
D3 的退役要同时改 `note-settlement-membership-facade` 自己的枚举,而那条路径
**从 `rememberTool` 到不了**;D10 的 schema 迁移与 CHECK 收紧同理。两者都能在
「两个接缝」的验收套件保持全绿的情况下回归。

所以接缝是三个,外加迁移自己的既有守卫。除此之外**不加新接缝**:`mergeLaneTag` 的内部行为
已有自己的单元测试,`clear` 的实现应当落在同一个模块里,由主接缝的行为测试覆盖,不单独暴露。

### 各模块的测试

- **`remember` 工具**(主接缝):每个动词的成功路径 + 每条拒绝路径,断言拒绝**文本**说出了
  数量与出路 —— 拒绝信息是这批的主要产品之一。
- **`clear` 的边处置**:断言只属于该泳道的边**行消失**,而不是两侧变空;
  断言跨泳道边在无 force 时拒绝、有 force 时删除。这是 D5 的要害,必须有独立的钉子。
- **`delete` 的守卫**:非空拒绝,空则删除;任务的守卫要同时覆盖「有成员」与「有泳道」两个分支。
- **任务合并**:四个 population 各一条断言。字段拼接单独一组(去重、title 取舍、散文分隔)。
- **地址解析**:`E<n>/#<tag>` 合法、`E<n>/#` 与非规范 tag 拒绝、与既有形式不串味。
- **rubric 文本**:现有的注入预算守卫(`MAX_INJECTED_BLOCK_CHARS = 9500`)必须重跑 ——
  改名会改变字节数。
- **console**:文案改动走现有的 DOM-rule 字段表,重新生成 `console-shell.ts` 并让陈旧守卫过。

### 验收纪律

沿用本项目的**突变验证**:每条声明的性质,故意改坏实现的那一处,
指出哪个测试变红,再用 `/tmp` 文件副本还原(**不用 `git restore`**)。
必须各自过一次突变的:D5(删边而非清空)、D4(空才删)、D8(不带 force 时清单被打印)、
**D6 的顺序**(把泳道搬移挪到成员重写之后,必须有测试变红)、
**D6 的成员选取**(改回按 tag 选,必须有测试变红 —— 用一个 `create(members=[...])` 播种的、
不带任务 tag 的成员构造,并同时断言目标端归属与源端清空/最终删除)、
**D5 的侧解析**(改回比较裸字符串,用两段同名泳道构造)。

**Rev 3:后两条突变的 fixture 本身要补强,否则它们是空的。**

- **六步顺序**:fixture 里的成员**必须带一个已声明的泳道 tag**,并走真实的 tag/归属写入路径。
  一个不带泳道 tag 的成员,错误顺序也能通过 —— 写闸根本不会被触发。
- **侧解析**:只跑 `clear(force=true)` 是**无效的** —— 裸字符串逻辑判「内部」然后删,
  正确逻辑判「跨泳道」然后 force 删,**最终存储一模一样,突变照样绿**。
  必须先断言**不带 force 时拒绝**、打印出对面泳道、边行原封不动,然后才断言 force 删掉。
- **D5b**:另加一条 —— 被删的行是该 pair 最后一条关系、引用方正文未变时,bare 行必须回来。

后三条是本轮 peer 找出来的三个 blocker,它们**当前都无法被任何测试发现** —— 这正是要给它们
配突变的理由。

## 不在范围内

1. **任务 `status` 与泳道 `closure` 的统一。** 段的 open/closed 是手动开关,
   泳道的是从 index 边推导 —— 同一个想法两套机制,是比命名更深的概念完整性问题。
   本批只统一动词,不动这一条。**记在这里,不是忘了。**
2. **通用的批量 tag 编辑器。** 能想到的批量操作只有两个 —— `merge`(改归属)与
   `clear`(去归属),`E<n>/#<tag>` 是它们共同的寻址方式。第三个用例出现之前不建。
3. **边的两侧持有任务 tag。** 「把泳道并回任务级」需要边侧能记任务 tag,
   而边侧今天只认已声明的泳道(E4 子集校验)。那是把「同一份词表的两级」贯彻到边上,
   是真正的模型推广,不是本批的小改。今天要跑的 21 条合并一条都用不到。
4. **强制删除非空容器。** `clear` + `delete` 两步已经覆盖,`delete` 不需要 force。
5. **第二批 17 条小泳道的去留判断。** 21 条子集合并会改变成员集合,
   现在下判断是拿旧地图。合并做完再看。
6. **存储层改名。** 表名、列名、代码标识符不动,见 D1。
7. **选举与校验器的重新设计。** 继承 v12 spec 的同一条约束。
8. ~~撤销一条关系边会抹掉该 pair 的唯一图记录~~ —— **Rev 3 收回这条驳回,已进 D5b。**
   驳回的理由(「既有不对称」)经查是假的:那个缺陷早已在撤销路径上修好,`clear` 会把它引回来。
9. **`force` 的确认令牌。** 见 D8 的取舍说明。
