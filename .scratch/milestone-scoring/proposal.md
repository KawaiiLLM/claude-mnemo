## 问题

0.8.4 的注入按 `tokenBudget=2500` 渲染弧视图，但生产实测 166 个会话中 **12 个（7%）超预算**，最差 S11387（741 turn）**9958 token**，是预算的 4 倍。12 个全部带「anchor rows kept in full」注记——即 fitter 已砍光 desc、移除全部非锚单元，**纯锚集合**仍是预算的数倍。

锚超预算本是设计允许的残量（spec §D：「锚集合是唯一允许的超预算残量」），但当时按「少数端点＋个别 G4」估量级，没有计入 **corrector 晋升无上限**：每个修正被推翻结论的 turn 都晋升 G3 并进入不可移除锚集合。S11387 的 76 个锚里 63 个是无标记 G3（corrector），S1730 是 55/62。长调试会话回滚几十次就产出几十个不可移除锚。

## 实证（盲选对照实验）

方法：6 个会话（覆盖 legacy 与 task-causality 两种引用形态、170–870 candidate turn），盲选 GOLD——模型只见 prompt 号/type/title/desc/文件/工具数/时间戳，不见等级、分数、引用数据，选出重建决策弧所需的 K≈12% turn。指标为**带内 AUC**（只比同 effGrade 对的排序，0.50=无信息）；overlap@K 降为次要指标，因为 K≈12% 时结果被 effGrade 主导、所有变体共享 effGrade，只剩约 3 个百分点分辨力。两指标排序一致。

**现行公式三项里两项无效**：

| 项 | 带内 AUC | 判定 |
|---|---|---|
| `isPureSpecTurn` | 0.500（6/6） | **结构上永不命中**——正则锚 `^docs/…`，但 `files_modified` 存绝对路径。全库 0 条可匹配（已独立复核） |
| `hasInsight` | 0.518 | 噪声 |
| `inDegree`(cap 2) | 0.539 汇总，按会话 0.45–0.69 | 唯一有效项，但不稳定；且全库仅 5 条结构化引用边，今天入度全部来自行内 `[T<n>]` 适配器 |

整体：V0 均值 0.567、最差 0.43（**2/6 低于随机**）。锚集合内（降级实际发生处）V0 均值 0.534、最差 **0.11**（S15440 近乎完全倒置）。

## 变更 1：替换带内 tie-break

```
tieBreak = 0.9 × ( 0.40·min(1, ln(1+|filesModified|)/ln6)
                 + 0.20·min(1, ln(1+gapAfterSec/60)/ln31)
                 + 0.20·min(1, ln(1+inDegree)/ln5)
                 + 0.20·min(1, ln(1+respLen/500)/ln21) )
```

`gapAfterSec` = 窗口内下一 turn 的 `createdAtEpoch` 减本 turn；`respLen` = `assistantResponse.length`。四项均读 `TurnRecord` 既有字段加选择层已算的入度映射，**零新增管线**。上限 0.9 由结构保证（四个 [0,1] 项、权重和为 1），不需 clamp——「分数不得跨等级档」的锁定约束继续成立。

权重非承重：等权 0.25×4 得 0.682 vs 0.684；留一会话交叉验证 held-out 0.685，但最优点把 `respLen` 压到 0.5 以上——冗余代理、可被啰嗦提取器操纵，故不采用。推荐权重是最优点噪声内的整数。

## 变更 2：锚集合降级（端点豁免）

fitter 现有两轮（砍 desc → 移除非锚单元）后直接输出超预算注记。新增第三轮：**锚集合自身超预算时，按同一分数序从低到高降级/移除锚**，硬底为结构性锚。

端点必须显式豁免。实测（已独立复核）端点在锚集合里排最后：

```
S11387  origin T1 → 75/76 (score 1.0)    S1730  T1 → 60/62 (2.25)    S15069  T1 → 16/17 (0.5)
```

端点靠**位置**进锚集合（结构性），分数却来自 effGrade，而会话首条常是低等级开场。不豁免则按分数降级会**第一个删掉弧的起源**。这也解释了实验里 gold 起源覆盖率 6 个会话仅 0–1 个。

## 变更 3：删除死正则项

`MILESTONE_PURE_SPEC_RE` 与 `MILESTONE_TIE_PURE_SPEC_WEIGHT` 随变更 1 一并删除。

**已知推断缺口（不得含混）**：「0.500 in 6/6」是因为它**从未触发**，不是「修好后也无用」的证据。若认为「改动 spec 文件」本身有信号，正确做法是先修正路径匹配再测量，而不是直接删掉当作已证伪。本提案选择删除，理由是：产物信号已由 `filesModified` 计数（0.623，最稳单信号）承载，再加一个未经测量的文件类型项属于无依据的复杂度。

## 变更 4：时序排序改用 transcript_line_start

独立缺陷，与上述同批修复。`claimCompactBoundaries` 的插入分支用 `maxPromptNumber + 1` 编号新发现的边界，即按**插入顺序**而非 transcript 位置。0.8.5 排干 13 天积压后，S15069 的 10 个 compact 标记按真实位置排序编号为 `51, 201, 202, 204, 105, 205, 206, 138, 208, 209`——`content_prompt_id` 与 `transcript_line_start` 均正确，唯一错的是 `prompt_number`。

旧 PostCompact 路径有同样漂移（105 真实槽位在 96/97 之间，138 在 126/127 之间），只是跑得近实时、漂移仅 8–12 位。

全仓 **8 处**按 `prompt_number` 排序、**0 处**按 `transcript_line_start`：

```
db/turns.ts:498,516,530   db/settlement.ts:169   db/citations.ts:435
db/orphan-turns.ts:39     hooks/capture-repair.ts:435   worker/processors.ts:345
```

主张：`prompt_number` 是**身份**（`[S12/T3]` 选择器依赖它，不可重编），`transcript_line_start` 是**时序真值**，今天两者被混用为同一列。修法为排序改用 `transcript_line_start`、NULL 回退 `prompt_number`。覆盖率 9440/9760 = 96.7%（缺的 320 条中 309 条为 era 前旧数据，新数据仅缺 11 条）。

替代方案（位置插入重编号）被 `UNIQUE(session_id, prompt_number)` 挡住，需整段级联重编号，且会破坏既有对外引用。

## 已知风险与待审问题

1. **污染**：盲选评委见过文件数与工具数，故此二者部分自我实现。剥离两列的对照基准显示：工具数 0.63→0.53（**基本是假象，已排除出公式**），文件数 0.62→0.58（部分假象但仍为正）。**注意生产现行的次级 tie-break 正是 `toolCallCount DESC`**（`compareMilestoneRank`），即被证明为假象的信号，本提案应一并处理。`filesModified` 权重 0.40 是否在剥离污染后仍站得住，需审。
2. `gapAfterSec` 在窗口末条 turn 上无「下一条」，边界取值未定义。
3. 变更 4 改变排序会连带改变分页、结算 K=50 的窗口归属（`type='compact'` 计入 K），以及引用解析顺序；compact 标记从尾部回到中部会重划窗口边界。
4. 端点豁免后，若某会话 era G4 锚数量本身即超预算，第三轮仍会退化为「照常渲染＋注记」。是否给 G4 也设降级次序未定。
5. 实验语料 6 个会话全部来自本机单一用户，形态覆盖有限。
