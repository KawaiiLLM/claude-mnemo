# 01 — note 的调用方身份校验

**What to build:** `note(turn:"S…/T…")` 目前接受任意地址，没有任何东西检查调用方就是那个 turn 所属的会话。生产实测 278 次调用 0 次跨会话，所以这不是在救火，是把一个靠自觉维持的约束变成机器维持的。

**Blocked by:** None — 但**设计尚未定案**，见下方调查结论。不要按「读环境变量就完事」实现。

**Status:** blocked-on-design

## 调查结论（2026-08-11，已在生产环境实测）

一条已经过期的源码注释声称 Claude Code 不把会话身份交给 MCP 进程。**不对**：`CLAUDE_CODE_SESSION_ID` 确实在 MCP 服务进程的环境里。

但直接拿它做校验会**炸**，而且炸法正是本项目最不能接受的那种——笔记静默停写：

- 实测当时，MCP 进程的 `CLAUDE_CODE_SESSION_ID` 是 `bbdd272a-…`，而库里**根本没有这个会话行**。
- 同一时刻，mnemo 正把 turn 写进 S15069，其 `content_session_id` 是 `e8541c19-…`，最新的 turn 就是那一刻创建的。

也就是说，**hook 侧与 MCP 侧对「这是哪个会话」给出不同答案**。环境变量命名的是*进程*的会话（会话被延续／恢复后会换新），而 mnemo 按*内容*会话记账。照环境变量校验，会把延续会话里的每一次 `note` 全部拒掉。

**候选设计**：只有 hook 同时握有两个 id——它收到 Claude Code 传来的内容会话 id，自身进程又带着 `CLAUDE_CODE_SESSION_ID`。因此由 hook 落一条映射（进程会话 id → mnemo 会话行），MCP 侧凭自己的环境变量查这张表。查不到时**放行而非拒绝**：没有身份不等于身份不符，拒绝会把没被覆盖到的路径变成静默停写。

**实现前必须先验证的前提**：hook 进程收到的内容会话 id 确实是 `e8541c19` 而它自己的 `CLAUDE_CODE_SESSION_ID` 是 `bbdd272a`。上面的结论是从「库里没有 bbdd272a 的行、turn 却在往 e8541c19 落」推出来的，还没有直接观测到 hook 那一侧的两个值。

- [ ] 先验证上述前提，确认后再定设计
- [ ] 地址所属会话与调用方会话不符时，`note` 拒绝并给出可理解的错误
- [ ] 身份**无法确定**时放行，并且这条路径有测试
- [ ] 延续会话（本票调查时所处的那种状态）里 `note` 仍然正常工作——这是本票最重要的回归
- [ ] worker 自用的工具通道不受影响（它没有、也不该有会话身份）
