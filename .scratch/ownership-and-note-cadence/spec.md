# 所有权归位与笔记节奏

## Problem Statement

结算 subagent 被压了四件事：打等级、维护边、判归属、重建笔记。四件里有三件它做不好，而且原因是结构性的，不是模型不够强。

**归属**：实测结算判断成员归属时，每个挂靠段只看得到 `[E49] [open] 标题`——它的段块是手搓渲染器，不含六个 Working State 字段，而 `content`/`insight` 又没有任何工具能写。它在对段的 goal/constraints/decisions 全盲的情况下决定「这个 turn 属于哪个任务」。

**等级**：每一种赋值机制都漂了（详见 `.scratch/turn-edge-mechanism/spec.md`），该 spec 已取消评分。

**笔记重建**：结算重建的笔记不受主 agent 那套字段卫生与预算约束，且重建质量天然低于第一手记录。

**笔记节奏**：逐 prompt 的欠账提醒在结构上恒真——`listOwedNoteTurns` 把「turn 已结束」定义为「有更晚的 prompt 存在」，而契约禁止给进行中的 turn 写笔记，所以上一轮在下一个 prompt 到达的瞬间必然欠账。实测全库 shift-0 出现 **0 次**，shift-1 是众数。一个每次都出现的字段是把契约复述了一遍，信息量为零；而它维持的正是 [S15069/T781] 之前的裁决 25 试图逃离的错挂区（为 turn N 写笔记时人在 N+1，同话题连续则写串）。

## Solution

**所有权归位**：主 agent 独占语义记忆——turn 笔记、段字段、成员归属。结算只剩**维护边**一件事。

**笔记按积压触发**，不再逐轮提醒。**段维护提醒改挂时钟**，不再是写操作的回执。

## User Stories

1. 作为主 agent，我希望把 turn 派进段是我自己的动作，因为我刚做完这些工作，知道它属于哪个任务；结算只看得到标题。
2. 作为主 agent，我希望用一次调用把**一个区间**的 turn 派进段（「T840–T855 属于 E49」），因为一段连续工作通常属于同一个任务，逐 turn 调用既贵又不符合我思考的单位。
3. 作为主 agent，我希望每轮拿到当前 turn 的地址，但不被提醒欠了什么——地址是我即时更新段归属与边时要用的，提醒则是噪声。
4. 作为主 agent，我希望只在积压达到 5 条时被提醒补笔记，并且提醒持续到积压降回 5 以下，这样一次错过不会让积压静默增长。
5. 作为主 agent，我希望在一个段 20 轮没被维护时收到提醒——即使我这期间一次 `remember` 都没调用过，因为「没更新」正是要提醒的那件事。
6. 作为主 agent，我希望段的每个 Working State bullet 是它那条决策链的**当前状态**，而不是历史堆叠，这样一条被改了五次的决策占一行而不是五行。
7. 作为结算 subagent，我希望我的职责只有维护边，因为归属与笔记我都缺少做好它们所需的上下文。
8. 作为结算 subagent，我希望在积累 20–50 turn 时才被唤起，不必处理短尾巴。
9. 作为用户，我希望历史空洞由后续会话主动 recall 补写，而不是由一个重建者猜测，因为重建质量低于第一手。
10. 作为维护者，我希望笔记时机只有一个家——现行契约的规则二与本 spec 直接冲突，必须改写而不是叠加。

## Implementation Decisions

### 所有权

- **`remember` 增加区间归属**：接受一个 turn 区间（`S<n>/T<a>..T<b>`）或地址列表，一次调用把它们派进一个段。归属是段的写入，与 `create` 的 `members` 种子同一条路径。
- **结算的 `assign`/`propose` 退役**，归属门与其活动记录表一并移除。
- **提案降级为例外通道**：结算发现一簇无归属 turn 像一个任务时仍可留一条文本提案，供后续会话决定；它不是常规职责，也不是完成条件。
- **结算不再重建笔记**：duty 2、完成门里的笔记缺口检查、结算 turn facade 的写入路径整体移除。
- **结算窗口 20–50 turn，不处理短尾巴**。不足者留待下次累积。

### 笔记节奏

- **逐 prompt 注入当前 turn 地址，不带欠账后缀**。地址供即时的段归属与边操作使用。
- **积压提醒阈值 5**（沿用现有的 `NOTE_RELIEF_PENDING_THRESHOLD`），**持续重渲染直到降回 5 以下**（沿用现有行为，[S15069/T870] 用户确认）。
- **段维护提醒改挂会话侧时钟**：距上次维护 20 轮时提醒，不依赖用户先调用 `remember`。「不足 10 轮」的过度维护提示仍留在写回执上，两者分开。
- **改写笔记时机契约**，不叠加。现行三条规则里的第二条（「欠账在本轮第一批工具调用里结清」）与本 spec 冲突，须整体重写为「积压提醒出现时开一批补写」。第一条（只给已完结的 turn 写笔记）不变。

### 段字段

- **Working State 的每个 bullet 是其决策链的当前状态**，不是历史堆叠。同一条决策被修订时用 `replace` 换掉该行，而非 `append` 追加。字段描述须写明这一点——机制早已存在，缺的是契约。

### 已知后果

- 会话尾部不足 5 条的欠账，若无后续会话跟进，可能永远没有笔记。这是接受的代价：结算不再兜底，而重建质量本就低于第一手。

## Testing Decisions

只验外部行为：给定一组 turn 与一次调用，断言归属落在哪些 turn 上；给定一个积压计数，断言提醒是否渲染。

- **区间归属**：一次调用派进连续区间；区间跨越不存在的 turn 时的行为；与 `create` 的 `members` 种子走同一条写入路径的断言。
- **结算收缩**：归属门与笔记缺口检查移除后，一个只做边维护的窗口能正常完成；不足 20 turn 的窗口不被唤起。
- **提醒**：0 欠账无输出；4 条无输出；5 条渲染；降到 4 条后停止；20 轮未维护的段在**没有任何 `remember` 调用**的会话里也能收到提醒——这是当前实现做不到的那一条。
- **契约单一性**：笔记时机的措辞在工具描述与 SessionStart 文本中只出现一次，两处不得各说一套（0.11.1 的事故即出于此）。
- prior art：`tests/hooks/note-reminder.test.ts`、`tests/mcp/remember.test.ts`、`tests/db/note-settlement-completion.test.ts`。
