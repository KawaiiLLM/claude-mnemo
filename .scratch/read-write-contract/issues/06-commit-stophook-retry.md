**Judgment calls (flagged for review):**
1. Lease-timeout reclaim (dispatch never reports back at all) is classified `"deterministic"` — the spec doesn't explicitly cover this third case (neither a reported transient nor a reported deterministic failure). Chose the conservative reading consistent with "cap-3 dies" — one unreported timeout is now enough to abandon, versus three under the old regime. Flagging in case the intended behavior was to treat this as transient (infinite retry) instead.
2. "1+1" interpreted as 2 total attempts (1 initial + 1 retry), not 1. The spec's own text contains both "上限 1 次" (cap: 1) and literally "1+1" in the same paragraph — I went with the literal "1+1" arithmetic since it's the more specific statement.
3. Existing `'failed'` status is NOT retired going forward — it remains the mid-cap retryable-with-backoff state (a deterministic failure at attempts=1 of cap=2). Only a deterministic failure AT the cap produces `abandoned`. This keeps backoff behavior for deterministic failures (only transient loses backoff, per the literal spec text), which I judged the more conservative reading than removing backoff for both classes.
4. Historical exhausted `failed` rows (attempts already ≥ new cap 2 under the old cap-3 regime) are NOT retroactively flipped to `abandoned` or given synthesized debt rows during migration — only `failure_class` is backfilled. Fabricating debt provenance for old rows felt riskier than leaving them as `failed`-and-never-reclaimable, which is already how the cursor treats them (unaffected — cursor's resolved-check already covers `failed && attempts>=maxAttempts`).
