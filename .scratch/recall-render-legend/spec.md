# 渲染层导航样板：每次响应说一次，行内只留变化量

Status: ready-for-agent
Rev: 1 (2026-08-11)
设计来源: S15069 T489–T490 的实测与讨论。三处样板的字节数均在生产库/真实注入产物上量过，方法记在「Further Notes」。
适用范围: 读侧渲染层。不改任何存储、不改检索命中集、不改截断预算。

## Problem Statement

读侧渲染把「怎么继续往下读」当成**每个字段**的属性来写，于是同一句导航指令在一次响应里复读几十遍。三处，量过：

在真实数据（S15069/T485，49 条 observation，`truncate=150`）上实测的整段渲染：

| 渲染路径 | 样板占比 | 导航句次数 | `tool:` 重复行 |
|---|---|---|---|
| turn 展开（观察记录预览 5 条，最常走的一条） | **16.9%**（4,298 → 3,572 B） | 12 | 5 |
| observation 列表 `S…/T…/O*`（49 条全渲染） | **26.7%**（23,763 → 17,417 B） | 77 | 49 |
| timeline 注入渲染 | **3.9%**（560 B / 14,519 B） | 同一下钻命令 14 次 | — |

三项样板:每个被截断的字段挂一条 70 B 的「用 mnemo-replay 读全文」；每条观察记录在标签行说过工具名之后，`tool:` 行再说一遍；timeline 每个折叠日分组重复同一个下钻命令与会话号。

**注意占比的口径**：上表比的是整段渲染的字节数，不是「样板 ÷ 被它标注的那几个字段」——后者能算出 47%，但那个分母不是读者付的钱，会高估收益。

**根因在一层：可发现性被实现成了逐字段属性。** 它其实是逐响应属性——读者需要知道「有个逃生口」一次，不是 75 次。三处不是三个独立缺陷，是同一个错位的三处露头，所以修法必须是一条规则而不是三个补丁。

第二处还有额外来历：它是纪元切换的副产品。旧纪元的 observation 有提取器写的标题，标签行与 `tool:` 行说的是两件事；新纪元的 observation 没有标题，标签行回落成工具名，两行就变成了同一个词说两遍。

## Solution

一条规则：**导航指令每次响应说一次，行内只保留变化量。**

- 字段被截断时只留已有的省略标记，不再逐条附「用 mnemo-replay 读全文」；该句改为整个响应末尾的一行图例。
- 观察记录的标签行已经就是工具名时，不再单出 `tool:` 行。
- timeline 的「还有 N 条」只保留数量与范围，命令名归入同一条图例。

读者拿到的能力不变：省略标记仍然指出这里被截断了，`[O…]`／`[S…/T…]` 仍然印在行上作为地址，图例把这两者接起来。变的只是这句话被说几遍。

## User Stories

1. 作为读者，我在一次响应里只被告知一次「截断的内容可以用 mnemo-replay 读全文」，不必在 75 个字段上反复读同一句。
2. 作为读者，我仍然能一眼看出哪些字段被截断了——省略标记还在原处。
3. 作为读者，我要下钻时手边就有地址：观察记录印着 `[O…]`，turn 印着 `[S…/T…]`，图例告诉我拿这些 id 去哪读。
4. 作为读者，我看一条观察记录时不会读到同一个工具名两遍。
5. 作为读者，旧纪元的观察记录仍然给我提取器写的标题，`tool:` 行在那里补充的是标题没说的东西，所以它继续出现。
6. 作为读者，我在 timeline 里看到「还有 22 条，范围 T2..T24」，数量与范围是我要的信息，命令名只在图例里出现一次。
7. 作为读者，一次响应里如果没有任何东西被截断，我不会看到那条图例——它不是装饰。
8. 作为主 agent，我把省下的 1,500–1,800 token 花在真正的记忆内容上，同一个 truncate 预算下能看到更多正文。
9. 作为主 agent，我第一次使用 recall 时仍然能自己发现 replay 这条轴，不需要事先读过 skill 文档。
10. 作为主 agent，我在会话启动注入的 timeline 里同样受益，那是每个会话都要付一次的固定成本。
11. 作为用户，我的 token 预算不再被同一句话的复读吃掉近半的观察记录渲染。
12. 作为维护者，我看渲染代码时能读出「可发现性是响应级属性」这一条规则，而不是三处各写各的样板。
13. 作为维护者，我新增一种被截断的字段时，不需要再决定要不要给它挂提示——图例已经覆盖整个响应。
14. 作为维护者，观察记录的去重规则不带纪元分支：它判断的是「标签是否已经等于工具名」，两个纪元各自自然得到正确结果。

## Implementation Decisions

### D1 · 图例是响应级的，且按需出现

- 渲染层在组装一次响应时记录「本次是否发生过截断」，仅在发生过时于响应末尾追加一行图例。
- 图例同时承担三处的导航说明（截断可读全文、`[O…]`／`[S…/T…]` 是地址、timeline 的下钻命令），一行讲完，避免把一个样板换成三个样板。
- 图例的措辞不引入自造词，直接给命令名与 id 形态。

### D2 · 逐字段提示取消，省略标记保留

- 字段截断后只保留既有的省略标记，不再拼接导航句。
- 这条对所有层级一致生效（session 的 desc/decision/done/reference、turn 的 title/desc/insight、observation 的 in/out）。分层保留会让规则重新变成三份，且 session/turn 层本来密度就低、省不出什么，不值得换来一个例外。

### D3 · 标签与工具名的去重按事实判断，不按纪元

- 观察记录的标签行取「标题 → 工具名 → 兜底文案」的既有回落链。当最终显示的标签与工具名相等时，`tool:` 行不再输出。
- 判据是两者是否相等，不是 turn 属于哪个纪元。
- **更正（实测后）**：旧纪元的观察记录根本走不到这一行——它的视图不携带任何机械字段（工具名也不带，见 D5），因此从来就没有 `tool:` 行。本 spec 初稿曾写成「旧纪元有真标题因而必然不等，所以仍会出 `tool:` 行」，那是凭推理断言了一个不存在的行为；照此实现会把工具名转发给旧纪元，反而给每条旧记录**新增**一行，与 D5 直接冲突。相等判据本身仍然正确，只是它在旧纪元一侧永远不被触发。

### D4 · timeline 的下钻指针只留变化量

- 折叠日分组的尾行保留隐藏条数与 prompt 范围，去掉重复的命令与会话号。
- 会话号在 timeline 的表头已经出现过一次，视图名对同一次渲染是常量，两者都归图例。

### D5 · 明确不动的东西

- 截断预算（`truncate` 的默认值与上限）不变：本 spec 减的是标注，不是正文。
- 检索命中集不变：这里只改渲染。
- 直接寻址的输出形态不变：`[S…]`、`[S…/T…]`、`[O…]` 照常印。
- 旧纪元观察记录的字段构成不变（仍是提取器摘要，不给原始工具字段）。

## Testing Decisions

好的测试只断言**读者看到的字符串**，不断言渲染内部怎么拼的。逐字段提示的取消、图例的出现与否、`tool:` 行的去重，全部可以在渲染结果上观察，因此不需要新增接缝。

**接缝：一个，且用现有的最高点。** 断言 `recall` 与 `timeline` 的渲染结果字符串——即 `recallMemory(...)` 与 `timelineQuery(...)` 的返回值。这两个函数已经是现有测试的入口，本 spec 不引入新的可测点。

覆盖的模块：recall 渲染、timeline 渲染，以及两者共用的格式化层。

要测的行为：

1. 一次含多个被截断字段的展开渲染里，导航句只出现一次。
2. 没有任何字段被截断时，图例不出现。
3. 被截断的字段仍带省略标记。
4. 新纪元观察记录不出现与标签重复的 `tool:` 行。
5. 旧纪元观察记录（有提取器标题）仍然出现 `tool:` 行。
6. timeline 折叠分组保留隐藏条数与范围，不再重复命令与会话号。
7. 一次渲染的总字节相对当前实现明显下降——用一个可读的下界断言，避免把测试写成字节数快照。

现有先例：`tests/mcp/format.test.ts`、`tests/mcp/recall.test.ts`、`tests/mcp/timeline.test.ts` 已经在这个接缝上断言渲染文本；纪元分流的断言先例见 `tests/mcp/era-cutover.test.ts` 与 `tests/db/search.turn-status-filter.test.ts`。

## Out of Scope

- **observation 队列通道的拆除**（入队、worker 消费分支、每次工具调用的 worker 唤醒）。范围已在 S15069 T486 定过，与本 spec 无关：那是写侧，这里是读侧。
- **观察记录的检索索引修复**（已提交、未发版）。它决定这些记录能不能被搜到，本 spec 只管它们被渲染出来时长什么样。
- **truncate 默认值的调整**。省下样板之后是否顺势调小默认值，是独立的一次判断，需要它自己的实测。
- **注入侧的其他体积问题**（persona、日记索引、最近会话列表的条数与长度）。同属预算问题但不同根因。

## Further Notes

**测量方法（可复算）**

- 观察记录：对生产库只读渲染同一个 turn（S15069/T485）两次——一次用改动前的渲染源码，一次用改动后——比较整段字节数与导航句出现次数。不是估算，也不是把「样板 ÷ 被标注字段」当收益。
- timeline：对一次真实的会话启动注入产物（14,519 字节）统计 `→ timeline(id=` 出现 14 次，其常量段合计 560 字节。
- 两条路径都要报：turn 展开只预览 5 条观察记录，是最常走的一条；`S…/T…/O*` 才会把 49 条全渲染。只报后者会高估日常收益。

**不能牺牲的东西**

三轴读模型里，replay 是「原始指针」那一轴，而 recall 是它的入口。样板可以删，**入口不能删**——图例的存在正是为了让「没读过 skill 文档的读者也能发现 replay」这一条继续成立。把导航完全挪进工具描述看似更省，但工具描述是每次请求都在上下文里的东西，不见得便宜，且对已经在读输出的读者不可见。

**为什么第二处值得单独一条决策**

它是纪元切换长出来的新问题，不是历史欠账。旧纪元不会出现这个重复。把它和另外两处一起收进同一条规则，是为了避免留下「新纪元专用的渲染分支」——那正是概念完整性要防的缝合。
