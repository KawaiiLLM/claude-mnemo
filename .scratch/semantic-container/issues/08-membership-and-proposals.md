# 08 — Membership assignment + homeless proposals

**What to build:** During settlement the subagent assigns each substantive turn to one of the session's attached segments, tags as the primary signal; turns fitting nothing stay homeless (legal). When a homeless cluster looks like one task, the subagent emits a text proposal — turn addresses + a suggested title + a reminder to ask the user — stored for the next session's injection; never a database segment, never auto-adopted. At most three proposals surface, newest first.

**Blocked by:** 06 (the settlement pass it rides); 07 (the write surface it uses).

**Inherited from 07's licensed deviation:** the segment facade retires HERE — settlement's segment authority shrinks to membership writes within attached segments plus text proposals, and the completion gate's segmentation check re-keys accordingly (it currently rides the facade's duty-3 machinery; every window would refuse forever if the facade died without this re-keying).

**Status:** done — the segment facade retires (`note-settlement-segment-facade.ts` deleted), replaced by `note-settlement-membership-facade.ts` registered under the tool name `remember` (ADR-0007's "same tool quartet" — `note`/`remember`/`timeline`/`recall`, not a dedicated facade), with exactly two actions: `assign` (turn + segmentId, scope-gated to `context.attachedSegmentIds`) and `propose` (≥2 addresses + title, whole-call-rejects on any bad address). The completion gate re-keys to a JOB-level fact (`note_settlement_membership_activity`, new table) — empty attached set auto-passes; a nonempty one requires ≥1 landed assign/propose, regardless of per-turn coverage. ADR-0004 flagging is implemented as a mechanical, post-commit, read-only check (`db/note-settlement-summary-flags.ts`) over attached segments' `content`/`insight` only (never Working State) — two heuristics: citation-less, and a citation naming a turn superseded within this same window — surfaced on the operator-facing metrics sink (`NoteSettlementWindowMetrics.summaryFlags`), never in the agent-visible commit receipt. Judgment calls flagged for review: (1) the tool RENAME from `segment` to `remember` at the SDK registration layer, inferred from ADR-0007 + ticket 07's own deviation note, not stated verbatim in this ticket; (2) "tags the primary signal" read as descriptive (membership assignment is the authoritative signal), not a literal new primary/secondary membership flag — plain many-to-many via the existing `segment_members` table, no schema addition; (3) the completion gate's re-keyed unit is per-JOB, not per-turn — one landed assign/propose anywhere discharges the whole job's duty when the attached set is nonempty (a window with attachments but genuinely nothing assignable/proposable has no way to signal "reviewed, nothing fits" short of one call — accepted as a known limitation, no third verb added since ADR-0002 names only two); (4) "a reminder to ask the user" is NOT stored per-proposal — the renderer (ticket 10) is expected to attach that boilerplate at render time, matching "you store + expose a reader; ticket 10 renders".

**Review (accepted):** named re-checks 125/125; full suite 2061/1 (stale-bundle guard only); typecheck clean. All four worker judgment calls accepted — (1) the `remember` rename matches the brief's pinning, (4) the render-time reminder transfers as an owed item into ticket 10's brief. One worker mutation claim corrected on independent re-run: "removed the early-return → 23 red" is behavior-preserving as literally described (0 red — with an empty attached set both ternary branches return an empty array); a true property-breaking mutation (empty set demands activity) goes 19 red across 5 files including the named zero-attachment test, so the inherited "every window completes with zero attached segments" duty IS pinned — the worker's magnitude was right, its description of the mutation wrong.
