# Settlement execution repair — one session, a living worker, and the friction the audits priced

**Status:** ready-for-agent (Rev 5, 2026-08-30 — peer rounds 1-4 findings all resolved; round 4's lifecycle P0 dissolved by USER RULING S15069/T2083: the worker exits after ONE HOUR idle and the next worker-triggering hook event restarts it — the owner-token/run-lifecycle machinery of Revs 2-4 is retired wholesale)
**Provenance:** user rulings S15069/T2064 (campaign halted as waste; face-refusal beats toolset-swap), S15069/T2065 (one-agent intent was original T1994 ruling; worker lifecycle), plus two Opus audits over the first live windows (output audit: ACCEPTABLE; process audit: agent SOUND, system burned the tokens — S15069/T2069, T2070), plus peer review round 1 (NOT READY, 9 findings, all accepted — S15069/T2074). Measured basis: stage-1 full pass 111K context / 38 calls; stage-2 killed at 153K / 25 calls with zero edges written; 67% of the full run's 2.61M tokens burned after an unsatisfiable gate; ~900K of that after the agent had already delivered the correct diagnosis and was twice forced back by the stop hook.

## Problem Statement

The staged settlement shipped in 0.26.0/0.26.1 does the right work in the wrong execution shape. The user ruled ONE agent working in staged commits (S15069/T1994); the spec I derived turned the stage transition into a fresh SDK dispatch, so stage 2 cold-starts, re-reads the window stage 1 already held (the stage-keyed grant identity makes this mandatory, correctly, GIVEN two runs), and pays roughly a second window's context before writing a single edge. Around it, four system-side frictions the process audit priced: the stop hook teaches a tool name stage 1 does not have and force-revives a run that has correctly diagnosed an impossible gate; the finalize summary cap lives only in the tool schema and two independent agent instances each burned 3-4 probing rounds on it; non-writable nodes sit unmarked in the writable roster so every run rediscovers them by refusal; and the prompt's mandated ten-a-batch reads truncate long entries, which the write gate then correctly yields on. Separately, the worker exits 70 seconds after seeing no registered session — but a later-spawned worker never sees earlier sessions at all (tool-use hooks write the DB directly by design), so the console frontend goes dark while sessions are alive.

## Solution

One settlement session runs both stages: the run is taught BOTH stages' duties up front by one stage-neutral prompt, stage 1's finalize lands the same fenced transition, and the SAME session continues into the edge pass with its context, cache and read grants intact — commit is present from the start and refuses deterministically until the job row says `edges`. The scheduler calls this unified run once per claim; a run that dies after the transition is resumed at `edges` by a fresh cold run under a new generation — the only place the old two-run shape survives. The stop hook becomes stage-aware and bounded. The worker's lifecycle collapses to one rule (user ruling S15069/T2083): it exits after ONE HOUR of idleness — no HTTP request, no hook-fed work, no settlement in flight — and the next worker-triggering hook event (today's trigger set, unchanged) spawns it again; it never needs to know whether sessions live, so a later-spawned worker cannot be "blind" to anything. The three prompt/teaching frictions are repaired where they live.

## User Stories

1. As the settlement job, I want both of my stages executed by one agent session, so that the edge pass starts with the topic pass's context instead of re-buying it.
2. As the user paying for settlement, I want the stage-2 read pass to disappear from the happy path, so that a 50-turn window costs one context establishment, not two.
3. As the unified run, I want every duty I will ever owe stated in my PROMPT before I start, so that the untrusted-data law over tool results (which I must keep obeying) never collides with my own instructions.
4. As the stage-1 phase of the run, I want commit registered but structurally refused while the job row says `topics`, so that commit-unreachability is enforced by durable state rather than by which tools exist.
5. As the stage-2 phase of the run, I want my writes fenced by the stage the DURABLE ROW currently records, so that my post-transition writes stamp `edges` without anyone re-deriving my identity by hand.
6. As the stage-2 phase of the run, I want the grant ledger to honor what this same run's stage-1 phase read, so that the anchoring law (grants record what these eyes saw) holds without re-reads.
7. As a reclaimed job's fresh run, I want to inherit NO grants from any earlier generation, so that a zombie's reads never license my writes.
8. As the scheduler, I want to dispatch the unified run at most once per claim and judge its return by re-reading the row, so that a run that stops after its transition is a recorded failure with its stage preserved — never a silent second cold start.
9. As the operator, I want the transition to stay one fenced non-terminal transaction and the terminal commit to stay the sole publisher, so that the state machine's guarantees are untouched by the execution reshaping.
10. As the settlement agent, I want the stop hook to name the terminal tool my stage actually has, so that I am never told to call a tool that does not exist for me.
11. As the settlement agent, I want the stop hook to nudge me at most once per run, so that a stop I have reasoned my way to is treated as my answer, not as an error to be overridden twice.
12. As the operator reading a failed job, I want the run's final text in the failure record, so that a correct diagnosis (like the T41 wall's) reaches me instead of being discarded.
13. As the settlement agent, I want the writable roster to mark non-writable nodes (`[skipped]`, `[rolled-back]`, `[compact]`), so that I never rediscover by refusal what the dispatcher already knew.
14. As the settlement agent, I want the finalize/commit summary cap stated in my duty text with a concrete refusal target ("cut below 800"), so that the cap costs one edit, not four probing rounds.
15. As the settlement agent, I want the topic-word phase-token ban visible in my prompt (it is currently stated only for lane names while enforced on both), so that my first topic word for a turn is legal.
16. As the settlement agent, I want my prompt's read procedure aligned with the write gate's completeness demand — told that a truncated batch entry does not license a whole-field write, that the repair is one targeted re-read of that address, and that `pageSize`/`turn` are mine to raise for the initial sweep, so that the two rules read as one system instead of a trap.
17. As a user with the console open during active work, I want the worker kept alive by the very hook events my sessions produce, so that recall/timeline panels answer whenever I look.
18. As the machine's owner, I want the worker gone after one hour of true idleness, so that persistence never becomes a daemon — and I accept that a console visit after a long-idle stretch waits for the next worker-triggering hook event to revive it.
19. As the worker, I want ONE idleness clock — reset by any HTTP request, any hook-fed ingest, and any in-flight settlement or drain work — so that no second exit path can kill me while something still uses me.
20. As a settlement run whose lease was reclaimed, I want to be aborted rather than left running as a zombie, so that a wedged model call cannot keep writing against a claim that moved on.
21. As the operator of a manual campaign, I want spawn-then-dispatch to survive the gap between the two commands, so that the worker does not exit while I am still typing — one quiet hour is the only deadline.

## Implementation Decisions

- **One stage-neutral run, taught whole (peer P0-1).** The unified run gets ONE settlement SYSTEM prompt and ONE opening prompt that declare BOTH stages' duties, the union toolset (recall, timeline, note, remember, finalize, commit, lane_check and the remaining stage-2 faces), and the stage boundary itself: "finalize is your transition; after it succeeds, your remaining duties are the edge-pass duties stated below". The untrusted-data law over tool results stays byte-intact — finalize's tool result carries ONLY data (the frozen worklist, writable set with provenance, removed-side debts, lane-member snapshots), never duties; every instruction lives in the prompt, the trusted channel. Stage-gated tools refuse by reading the durable job row's `stage` at call time — `commit` while `topics` refuses deterministically naming `finalize`; stage-1-only refusal behaviors (note's relation-field refusal, remember's merge/justify refusal) key on the row the same way. The refusal IS the unreachability mechanism (user ruling S15069/T2064). The current stage-2 opening prompt survives only as the cold RESUME prompt (below).
- **One dispatch per claim; the chain verdict retires (peer P0-2).** The scheduler calls the unified dispatch at most once per claim and judges its return by re-reading the row: row `done` under the same (job, generation) ⇒ settled, whatever the verdict said (post-hoc truth, now anchored at the terminal end); row still `claimed` at `edges` ⇒ this run finished its transition but not its window — recorded as a failure WITH the preserved diagnosis, stage kept, attempts spent normally; row still `claimed` at `topics` ⇒ handled as reported. The `chain` verdict and its same-drain re-dispatch are DELETED — their tests rewritten, not preserved — because under a unified run a post-transition return IS the run's answer, and chaining it would silently buy the second cold session this spec exists to abolish. The next claim (a NEW generation) resumes at the recorded stage: an `edges` resume is a cold stage-2-shaped run (today's shape, now the retry path only), a `topics` resume re-runs the unified shape.
- **Two-layer identity: write capability by CALL-ORIGIN stage, grant principal by (job, generation) (peer r1 P0-3 + r2 P0-1).** (a) Write capability is bound to the stage the CALL ORIGINATED under, never to the row's stage at execution time — and the origin is observed at a NAMED mechanical seam (peer r3): a RESPONSE-ORIGIN COORDINATOR in the SDK-query host. The API's assistant `message.id` is the round boundary (the SDK preserves it on every assistant message; a new id begins only after the previous response's full tool-result set has drained back to the model). The host's message loop — which today skips every non-`result` message and must stop doing so — freezes the origin stage at the FIRST block it sees of each new assistant `message.id` and maps every `tool_use.id` in that message to that immutable origin. A write face resolves its own call's origin through the MCP handler metadata key that carries the tool-use id (`claudecode/toolUseId` — a private Claude Code key, so an adapter SENTINEL test pins its presence and an absent/unknown mapping FAILS CLOSED, never falling back to the durable row's stage; the SDK dependency's version coupling is part of the contract). finalize changes the durable row and thereby the origin of FUTURE assistant message ids only; sibling calls in the same message keep their pre-transition origin and refuse deterministically ("stage advanced mid-response — read the finalize result, then re-issue"). A new assistant `message.id` is, by the protocol above, the observable fact "the model has received the finalize result" — that is where edge-pass capability begins. The handler-scheduling race (a handler may run before the host loop observes its assistant block) is closed by the handler WAITING for its mapping rather than guessing — and the wait has a MECHANICAL TERMINATION contract (peer r4): it is abort-aware and resolves to a REFUSAL on whichever comes first of the assistant response/stream ending without the mapping, the query aborting, or a short coordinator deadline; the registry's dispose rejects every pending waiter; absent metadata refuses immediately; no code path may hold an unbounded promise. The existing leased-tool wrapper, which currently drops the handler's second argument, is reworked to thread the metadata through. This is the same-generation stale-context protection the old stage-keyed identity provided, kept mechanical; a stale RECLAIMED context remains fenced by generation as before. (b) The grant principal for every authorization family — read grants, per-field completeness, the relations gate, the session-narrative grant, lane-read receipts — is `(job, generation)`: an `edges`-stage gate check honors grants recorded under the same generation's `topics` identity (one run, one set of eyes), and a new generation inherits nothing from any predecessor. The write-gate freshness comparison stays untouched. Implementation shape: a grant-principal resolver both gate directions share, over the existing tables' writer/reader strings — the stored strings keep their stage component (no migration); the CHECK widens to the generation's pair. Read principals may span the stages; write capability never leaves its origin epoch.
- **The call-origin gate protects the transition-CAPABLE run only; the cold `edges` resume stays origin-blind, by documented narrowing (settlement-execution-repair ticket 13, implementation-review P2 sweep item 3, deferred from Rev 5's original blanket wording).** Rev 5's "an absent/unknown mapping FAILS CLOSED" clause, read literally, would gate every write face on every settlement dispatch — but the coordinator exists to stop a call composed BEFORE a mid-response `finalize` from inheriting the AFTER-transition stage from the durable row alone, and that failure mode requires a dispatch that can transition mid-run. The cold `edges` resume (the retry path a dead unified run falls back to, per this same bullet's own dispatch rule two bullets up) is spawned already AT `edges`, under a fresh generation, and every call it ever serves wants that one fixed stage — there is no earlier-response mapping for a later call to wrongly inherit, so the coordinator's own failure mode cannot occur there by construction. Reusing the coordinator's per-call gate on that path anyway was evaluated and rejected as disproportionate: it would force every existing caller of that dispatch's `note`/`remember`/`commit` handlers (spanning several pre-existing test files well outside ticket 13's territory) to start supplying observed `_meta["claudecode/toolUseId"]` metadata that path's own tests already document as unnecessary (`staged-settlement-integration.test.ts`'s `scriptedResumeQueryImpl`: "no origin staging needed, it has only one stage to be"). What already guards the cold path is the generation+stage CAS every write goes through regardless (`assertNoteSettlementJobClaimed`), unchanged by this narrowing. See `note-settlement-sdk-query.ts`'s own comment ahead of `createNoteSettlementSdkQuery`'s `leasedTool` for the full reasoning, and `tests/worker/note-settlement-response-origin.test.ts` for the pin.
- **The frozen scope is installed by an internal handoff, not re-derived (peer r2 P0-2).** At unified-run start the transition snapshots do not exist, so the run opens under the stage-1 scope authority exactly as today. The finalize handler — after its transition transaction commits, before its tool result returns — reads the just-persisted frozen scope ONCE and atomically installs it as the run's edges context: the writable set with provenance classes (removed-side-citer members included), the ordered worklist, the removed-side debts and the lane-member snapshots. Every subsequent relation write, lane_check, terminal gate, and shape/retraction capture consumes that one cached context; nothing recomputes scope from the live graph per call, so post-transition graph changes cannot widen what the run may touch. A cold `edges` resume reads the same frozen scope once at query construction, as today.
- **One idleness clock, one hour, no session knowledge (USER RULING S15069/T2083 — retires Revs 2-4's owner-token/run-lifecycle design wholesale).** The worker never asks whether sessions live. Its lifecycle is a BUSY/IDLE state machine (peer r5): `busy` = any active NON-CONSOLE HTTP request OR any tracked drain/settlement/dream work genuinely live (`/console` and `/api/console/*` keep their pre-existing idle-lease exemption — browsing must never keep the worker resident, or an open auto-polling tab would make it immortal; an in-flight console response still finishes before any exit via the unconditional in-flight guard — ticket 08 adjudication) — a busy worker never exits, however long the work runs (a 70-minute drain does not fall through the threshold at its end); when the LAST busy token releases — a work item completing, or the claim monitor's abort verdict landing on a query that will not settle — `idleSince` is set atomically to that moment, and any new request/ingest/work-start clears it. A full quiet HOUR from `idleSince` (config-owned constant) triggers shutdown; the shutdown itself is BOUNDED — graceful cleanup with a forced-exit fallback (the shape the old hard-exit path already carries), so an abort-ignoring promise cannot hold the process past its deadline and "bounded by one hour" stays true mechanically. Busy tokens pair start/end exactly once; an abort does not double-release. The next WORKER-TRIGGERING hook event spawns it again through the existing on-demand path (peer r5 P2: the trigger set stays exactly today's — session boundaries, Stop, PreCompact — tool-adjacent hooks and UserPromptSubmit keep writing the DB only, per the 0.9.3 red line; no new pings). During active work those triggers revive and re-feed it continuously, so the console answers throughout a working day; after a long-idle stretch the first triggering event brings it back. RETIRED BY THIS RULE: the 70-second "all registered sessions closed" hard-exit (the registration-blindness that killed manually spawned workers and darkened the console), the 30-minute idle-HTTP shutdown as a separate path (its clock folds into the one rule), and every owner-token/run-generation/liveness-probe mechanism the earlier revisions designed — peer round 4's token-less residual dissolves with the machinery. `session_run_state` stays exactly as it is. Accepted consequences, per the ruling: a crashed session's worker lingers at most one idle hour; a console visit after >1h of no activity waits for the next triggering event.
- **The reclaimed run dies instead of haunting, watched by its own monitor (peer r1 P1-6 + r2 P1-4).** The unified dispatch holds an AbortController for its query AND an independent, cancellable claim monitor beside it — a timer keyed to the lease deadline (or a modest interval) that re-reads the durable `(job, generation, status)` row; a wedged model call that never issues another tool call therefore still gets observed. Generation, status or lease loss fires the abort; the monitor is cleared when the query settles. The in-call fences remain, but they are correctness checks, not the stall detector. A wedged run that survives its abort is bounded by the one-hour idleness exit like everything else (in-flight work resets the clock only while the work is genuinely live — an aborted query stops counting as work).
- **Stop hook, stage-aware and bounded.** The hook reads the job row: stage `topics` names `finalize`, stage `edges` names `commit`. It nudges at most ONCE per run; a second stop without the terminal call is accepted as the run's answer and flows into the failure accounting above. The declarative escape hatch the process audit sketched (`finalize(blocked=[...])`) stays REJECTED: a gate an agent can declare its way past is not a gate; unsatisfiable gates are bugs (the machine-namespace law), and the bounded hook plus preserved diagnosis caps the spin cost at one nudge.
- **Diagnosis into the failure row, with a pinned composition (peer P1-7).** The dispatch — not the scheduler — composes `last_error` as: stage marker + the mechanical conclusion ("stopped without commit" / gate text) + the run's final assistant text, truncated ONCE to the existing 500-character error budget with the assistant text's TAIL preferred when something must go (the diagnosis conventionally ends the text). No path may replace this composition with a generic reason once a final text exists; the retired chain branch's discard behavior dies with it.
- **Roster annotation.** The prompt's writable-set listing marks each non-writable node with why (`[skipped]`, `[rolled-back]`, `[compact]`), sourced from the same predicates the write faces refuse by, and states that no duty applies to them.
- **Teaching repairs, where the agent can see them.** The finalize and commit duty paragraphs state the 1000-character cap with the refusal target ("shorten below ~800"); the topic-word duty states the phase-token ban with the family examples (the same vocabulary the refusal enforces); the read procedure recommends raising `pageSize` (which the recall face already has — peer P2-9, narrowed from Rev 1's false "exposes" claim) and `turn` for the initial sweep, and teaches the yield-repair idiom (one targeted re-read of the yielded address; metadata filter suffices for type/tags).

## Testing Decisions

- Execution reshaping at the HIGHEST existing seam (peer P1-8): the staged-settlement integration suite — real stage registrations, real scheduler, only `queryImpl` swapped. Happy path: ONE `queryImpl` call per claim, finalize and commit landing through the SAME handler registry, job `done`, attempts spent once, and a grant-carry assertion (an edge write whose only qualifying read grant was recorded pre-transition lands without a re-read). Retry path: kill between transition and commit ⇒ failure recorded with stage `edges` and the diagnosis in `last_error`; next claim runs a NEW generation, `queryImpl` called once, edges-shaped, inheriting no grants. The stub-stage idiom survives only for scheduler arithmetic that predates the reshaping.
- Chain-deletion honesty: the existing chain tests are REWRITTEN to pin the new verdict handling (a post-transition return records a failure, never a second dispatch) — deleted behavior gets deleted tests, not preserved ones.
- Commit-refusal-by-stage pinned at the same integration seam; all existing gate-refusal texts byte-unchanged.
- Stop hook: existing unit seam — stage-aware naming, the once-per-run bound, and the two-stops shape asserting failure accounting with preserved text.
- Worker lifecycle at the timer seam with an injected clock, as the busy/idle machine: a 70-MINUTE live drain does not exit at any point, and `idleSince` starts only at its END (59 further idle minutes no exit, 60 exit); a query that received its abort but never settles releases its busy token at the abort verdict, and when the hour lands the BOUNDED shutdown exhausts its grace and calls the forced exit (pinned: process exit happens despite the unsettled promise); busy tokens pair start/end exactly once and an abort does not double-release; a freshly spawned worker with no registered sessions and no jobs survives well past the old 70-second horizon (the retired hard-exit pinned dead); the retired 30-minute idle-HTTP path is gone (a live drain at minute 40 of HTTP silence does not exit).
- Abort path: a never-resolving `queryImpl` + fake clock + a lease reclaim ⇒ the independent claim monitor fires the abort observer — no tool call ever runs, so the test proves the monitor, not the in-call fences.
- Call-origin coordinator, two layers (peer r2 P0-1 + r3 + r4): a pure registry unit — same-message finalize→commit/relation refusal, new-message-id success, text-first block freezing, handler-before-observation waiting THEN succeeding, an unknown id refusing when its response closes without the mapping, a query abort refusing and clearing the waiter, dispose leaving zero pending waiters, absent metadata refusing immediately, a new generation clearing the table; then the integration seam yielding real assistant ids A/B through the host loop with handler metadata threaded (the reworked leased-tool wrapper), pinning the end-to-end refusal and next-round success. A sentinel test pins the `claudecode/toolUseId` metadata key against SDK drift — key gone ⇒ writes refuse safely, suite red. Stage-1-era refusals (relation fields, commit) and post-transition refusals (tags/type writes where stage 2 forbids them) stay pinned.
- Frozen-scope handoff (peer r2 P0-2): a turn that enters the stage-2 writable set ONLY via the removed-side-citer closure gets relation-only authority through the same handler registry after finalize; mutating the live graph after finalize does NOT widen the run's scope. The grant-carry test does not substitute for this scope test.
- (The Rev 2-4 lifecycle-attribution test family is retired with its machinery — the user's one-hour rule needs no session attribution at all.)
- Prompt teaching via the prompt-pin idiom (needle tests) for the union duty declaration, the data-only finalize result contract, the roster annotations, the cap sentence, the topic ban list, and the pageSize/turn recommendation.
- Mutation discipline as standing law: each behavioral repair gets one reverted-alone mutation that kills exactly its own test.

## Further Notes

- The token arithmetic that justifies the reshaping: stage-1 full pass ended at 111K; the killed stage-2 spent 153K re-establishing before its first write. The single-session shape bounds the whole window at roughly stage-1's cost plus the edge-writing rounds on a cached prefix — comfortably under compact limits for 50-turn windows; if a future window shape approaches the limit, the retry path IS the pressure valve (a deliberate transition-then-exit remains legal: the run stops, the failure records "transition landed", and the next claim cold-resumes at `edges`).
- The stop-hook tool-name bug (`commit` taught to a stage-1 run) burned ~900K tokens across two forced revivals in the audited run; the once-per-run bound caps that class at one nudge.
- The one-hour idle rule respects the 0.9.3 cache red line untouched (tool-use hooks keep writing the DB directly); the hook events that DO reach the worker — session boundaries, flushes, spawn-on-demand — are what reset its clock and revive it, and no session-liveness knowledge is needed anywhere. Peer rounds 2-4 designed and then the user's ruling retired a full owner-token run-lifecycle (the drafts live in this file's git history); the lesson stands recorded: process lineage is an observation, not an ownership protocol, and a liveness guarantee that needs one should be traded away rather than built on a guess.
- Peer round 1 (NOT READY, 9/9 accepted) reshaped Rev 1's five weakest sentences into the five leading implementation decisions; the reviewer's evidence lines were verified against source before adoption (stage-1 SYSTEM's untrusted-result law, the chain branch's re-dispatch, the tuple-keyed grant families, the two-column `session_run_state`, the HTTP-only idle shutdown).
