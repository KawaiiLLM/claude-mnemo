# turn 边机制：重要性从赋值改为推导

## Problem Statement

turn 的重要性一直靠**赋值**得到，而每一种赋值机制都漂了：

- 主 agent 打的 0-4 等级通胀，用户判定「太主观、打分漂移严重」[S15069/T818]；
- 换成带内绝对评分后实测同分组占 93–100%，次级键成了实际主排序（2026-08-04 空结果实验）；
- 换成 A/B/C 差额选举后，本轮实测在四档紧上限下**三档全部精确填满**（A=5 B=10 C=15，恰好等于上限），而同一模型同一窗口在松上限下只选 6 和 12 并明确拒绝填满。上限一旦窄到够得着，就不再被读成上限。

与此同时，本可以推导出重要性的边一直定义不清，退化成「同一条工作流」的标签：一次实测里八个验货 turn 全部指向最初那次派工，形成星形；对该边表做中心度，排出来的前四名是发 spec、拆票、派工三个流程枢纽，而两次人工评选的 A 档只有一个进榜，**选举机制本身那一轮得分为 0**。

## Solution

**取消一切评分。** 重要性由边与 type 推导，而边与 type 的合法组合由工作流阶段决定。

三个阶段、四类关系、三条计分规则，全部可机械计算，没有一处需要「这一轮有多重要」这类裁量。

### 三个阶段

| 阶段 | type | 产出 |
|---|---|---|
| 取证 | research / measure | 事实 |
| 决策 | design / discuss / correction | 决策 |
| 落地 | implement / refactor / fix / delegate / review / ops | 工件 |

判据：**凡产出「承载决策的工件」者皆为落地**——spec、ADR、票、提交、发布一视同仁。故拆票属落地而非设计（[S15069/T896] 用户裁定）。

一个 turn 可携带多个 type。跨阶段的决策**必须**双 type：审查阶段动摇了设计就是 `["review","design"]`，否则设计决策与实现细节不可分辨。

### 四类关系，由阶段对推导

| 阶段对 | 关系 | 含义 |
|---|---|---|
| 取证 → 决策 | `evidence-for` / `evidence-against` | 检验某条主张 |
| 决策 → 决策 | `refines` | 决策线继续，可能改动其中一段 |
| 决策 → 决策 | `override` | 前驱的结论**是错的**，整体作废 |
| 落地 → 决策 | `encodes` | 这件工件承载了哪几条决策 |
| 落地 → 落地 | `depends-on` | 纯因果，本身无决策内容 |

没有一条关系是凭空设计的：每一条都是某个阶段对的唯一合法关系。

**边即直接因果**：前驱是**直接引起这一轮**的节点，不是「同一摊活的源头」。跳级指向弧起点属标注错误。

**孤儿合法**，且只有两类：未曾设想的子任务起点，与无决策关联的闲杂（解释概念、查进度、重发、compact）。二者以出度区分，不得为消灭孤儿而编造前驱。

### 三条计分规则

- **`override` 归零**——被 override 的 turn 重要性直接为零。全有全无，故可在节点粒度断言。稀有：51 轮的窗口里仅一处（一次源码误读被下一轮全盘推翻）。
- **`encodes` 抬升**——且是**唯一能救「一次定对、无人回头」的决策**的通道。实测：选举机制那一轮在纯 refines 图上得 0 分，靠 ADR 与 spec 两条 encodes 升至首位。
- **`refines` 只在超出链表基线时计分**——一条推进讨论的 turn 入度恰为 1，那是基线，不携带信息；**超出 1 的部分**才是「后续工作回头找它」。实测：选举那一轮收到 4 条，其中两条跨越 12 与 25 轮。计分时按**来源阶段**加权：来自决策阶段的细化重于来自落地阶段的细化，这自动把「阈值改动」与「机制提出」分开。

### `encodes` 取最小可推导集

一件工件只 encode **可推出最终结论的最小节点集**，剔除错误路径与冗余路径（[S15069/T896]）。

这条同时取消了 A 档：写 spec 的人为了写出 spec，本来就必须决定哪几条决策承重；把这个决定记成边是副产品，不额外花一次判断。实测——把某次 spec 的 20 条 encodes 收敛为最小集后，活下来的 7 条与人工评选的 A 档几乎重合。

## User Stories

1. 作为主 agent，我希望记下「是什么直接引起了这一轮」，这样后来的读者能沿因果回溯，而不必猜测顺序背后有没有关系。
2. 作为主 agent，我希望在发现前一轮**结论是错的**时记一条 `override`，这样错误路径不会继续污染任何视图。
3. 作为主 agent，我希望在写 spec／开票／提交时记下这件工件承载了哪几条决策，这样一次提交可以回溯到它依赖的全部设计裁决。
4. 作为读者，我希望从任意一次落地反向遍历，能走到它所依赖的设计决策，而不是走到 spec 就断。
5. 作为读者，我希望里程碑视图里同一条决策链只占一个一级行，其成员嵌套其下，这样五次修订不占五行。
6. 作为读者，我希望被 override 的 turn 不出现在任何一级行里，只作为地址出现在推翻它那一行的索引中。
7. 作为读者，我希望「后续反复回头引用」的决策自然浮上来，而不是靠谁给它打了高分。
8. 作为工具使用者，我希望在把 `refines` 记到一个纯 review 型 turn 上时被拒绝，因为那说明我要么记错了关系、要么漏标了 `design`。
9. 作为维护者，我希望不再需要维护纪元边界、席位上限、分布校验这些评分配套。
10. 作为维护者，我希望边质量差时视图退化成今天的平铺形态，而不是给出错误的分组。

## Implementation Decisions

**note 工具增加边／type 校验。** 一条边合法，当且仅当其两端 turn 的阶段对允许该关系（上表）。校验在写入时进行，拒绝时说明缺哪一半。

这条校验**自我强制正确的双 type**：想从一个 review 型 turn 记 `refines`，必须同时标 `design`，否则被拒。实测这会当场抓出两处真实错标——两轮审查各自推翻了一次设计裁决，却只标了 `review`。

**关系词表收敛为五个**：`refines`、`override`、`evidence-for`、`evidence-against`、`encodes`、`depends-on`。`supersedes` 退役——实测 10 条 `supersedes` **没有一条**作废了前驱的全部结论，每一条都只杀掉一段而其余照常上线；「被替换」永远是局部的因而与 `refines` 不可分，「是错的」才是全有全无。

**`depends-on` 记录但不计分。** 它是回溯链上落地段的必经之路，删掉它则从提交走不到设计；但对它做中心度只会量出工作流扇出。记录与推导用同一张图的两种投影。

**阶段由 type 派生，不另设字段。** type 已存在且已在用双值。

**不钉数值权重。** 本 spec 只钉信号与次序（override 归零 < 无信号 < 超出基线的 refines < encodes），具体权重待真实数据标定后再定；先钉数字等于再发明一次评分。

**退化保证。** 无边时链条分组退化为今日的平铺一级行。边质量是本方案唯一的真风险，退化把最坏情况锁定在「与今天持平」而非「比今天更糟」。

## Testing Decisions

好测试只验外部行为：给定一组 turn 与边，校验是否按关系表放行／拒绝；给定一张图，回溯是否到达预期的决策集。

- **校验层**：每个阶段对的合法与非法关系各一例；`refines` 记到纯 `review` turn 被拒且提示补 `design`；补上后放行。
- **回溯层**：构造 落地→票→spec→决策 的链，断言从落地可达设计决策；删掉 `encodes` 后断言在 spec 处断裂——这正是实测到的分区。
- **计分层**：链表基线为 1 的图上，全部节点同分；给某节点加一条跨越式 `refines` 后，仅该节点上升。
- **override**：被 override 的 turn 计分为零，且不出现在一级行。
- 现有 `tests/mcp/note.test.ts` 与边相关测试是 prior art。

## Out of Scope

- 数值权重的标定。
- 同一阶段内部「机制 vs 细则」的区分——两个机械代理(来源阶段、下游扇出)都测不准，扇出甚至会反向（一条把问题全部解决的裁决扇出低于一条留下许多待定的细则）。承认测不准，不硬造关系。
- 历史数据回填边。
- 词表可能还缺的关系：`follows-from`（前驱的发现引出新问题，后继自带内容）、`answers`（前驱明确提问被关闭）、`resend-of`、`discharges`（义务转移）。已实测到实例，但先不进本版。

## Further Notes

**待裁决两项：**

1. **活的决策在落地之前没有 `encodes`，因而里程碑视图只显示已结算的决策。** 默认判断是这样正确——段卡片的 Working State 承担「现在在哪」，里程碑承担「什么已经定了」，两块注入各司其职。若不认同，需要为未落地的决策另设浮现通道。
2. **`ops` 是否兼任「产出决策工件」这个语义。** 写 spec、开票、提交、发布现在都会落到 `ops`，而 `ops` 原义偏运维。可接受则不动，否则词表需要一个新词。
